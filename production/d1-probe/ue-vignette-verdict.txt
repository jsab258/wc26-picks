#   purpose: materials, the props and the HDRI are Phase C and Phase D.
# frameMedianMs: MEDIAN of 24 engine frame deltas after 8 discarded warm-up
#   frames, in milliseconds. NOT the Unity host's number even though both are a
#   median of 24 after 8: Unity times one Camera.Render plus GL.Flush and this
#   times a whole engine frame. frameStat on each line names which one it is.
# shotMeanLuma: mean over EVERY pixel of the committed file, 0 to 1,
#   luma=(0.299R+0.587G+0.114B)/255, the same weights the Unity sim uses.
# shotNonBlackPct: percent of shotPixels with any channel above zero.
# shotDistinctBuckets: distinct 5-bit-per-channel colour buckets, of 32768.
# a shot status of WROTE needs a decoded file with more than one bucket and
#   at least one non-black pixel. BLANK, UNDECODABLE and NO-FILE are the three
#   ways it fails, and the step exits non-zero for all three with the evidence
#   still committed.
# QUEUE 059, THE TWO MEASUREMENTS RUN 17 DID NOT HAVE. Its lantern count read
#   four of four and answered `were four lights created`, while both night
#   frames were black; its mean luma read 0.5030 over a day frame whose ground
#   plane was entirely clipped. Neither number could see it. These can:
# shotClipHiAny/shotClipHiAll/shotClipLoAll: COUNTS of pixels at the top and
#   bottom of the 8-bit range over shotPixels, never a mean. shotLumaBands is
#   eight equal luma bands, band 0 darkest: a printed series, not a bound.
# light lines: one per probed light, the SAME camera, condition and frame
#   counts as its shot with that one light switched off. deltaMeanFull is the
#   whole frame, deltaMeanPeak is the named grid cell in peakRegion, and both
#   halves of every difference are printed beside it (meanOn.. and meanOff..).
# THE CONTROL LINE TOGGLES NOTHING and is this run's own noise floor. A
#   lantern whose histogram does not clear the control's did not light the
#   frame. No threshold is set here: read the series, set the bound after.

#   the picture is not to be fixed before it is measured.
# PHASE C, MATERIALS. One surface line per surface the shared file asked for,
#   with what each map LOADED AS rather than what its filename claims, and the
#   candidates tried for every map that is not there. The base material is a
#   BUILD PRODUCT made by tools/ue/make_base_material.py in the cook step: no
#   human opens the editor, which is D1 measurement (a) in one line.
#   materialBase reads MISSING when the cook did not carry the asset, and
#   every surface below is then untextured however many maps decoded.
# PHASE C, THE READBACK. Each surface line carries what the material
#   instance answered when asked for the texture and the two tiling
#   scalars straight back, and the materials line carries the run's
#   totals over the surfaces a parameter was actually set on. It is the
#   GAME thread's copy: a value that lands there and never reaches the
#   render proxy still reads back as the same pointer.
# PHASE C, THE CONTROL QUADS. Three planes of one size at one distance
#   in front of the first shot's camera, off the same base material,
#   carrying no street data. The first binds a 2x2 texture built in code
#   from four saturated colours, with no file and no decode; the other
#   two bind no texture at all and differ only in their tiling scalars.
#   Four colours on the first means a texture override reaches the
#   sampler. Two different cell counts on the other two means the scalar

#   the quad lines say only where to look and what was asked for.
#   The controls occupy their printed boxes, so any whole-frame statistic
