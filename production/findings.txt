FAULT TWO, AND IT HAS BEEN THERE SINCE THE STEP WAS WRITTEN. The commit step's
every git call is malformed, and it would have failed a run that produced five
perfect PNGs:

    shopt -s nullglob
    G="git -c safe.directory=*"
    $G add -A -- "${FILES[@]}"

`$G` is unquoted, so the shell globs it, and the `nullglob` set two lines earlier
for the FILES array DELETES the non-matching `safe.directory=*` entirely. Measured
here rather than reasoned:

    $ shopt -s nullglob; G="git -c safe.directory=*"; set -- $G; echo argc=$#
    argc=2        # git, -c. The assignment's value is gone.

So the command runs as `git -c add -A ...`: `add` is eaten as the argument to `-c`
and `-A` becomes the subcommand. The log shows it four times over, `unknown option:
-A`, `unknown option: --cached` twice, `unknown option: -m`, ending
`artCommitStatus=COMMIT-REFUSED stagedPaths=0/1-matched`. The step cannot stage,
cannot diff and cannot commit.

THIS FAULT WAS HIDING BEHIND THE OTHER TWO, which is the transferable half. A
workflow that fails early never reaches its later steps, so every step after the
first failure is UNRUN CODE WEARING THE APPEARANCE OF WORKING CODE. Two failures
in a row moved the failure point forward and exposed it. The lesson is not "fix
the glob": it is that a lane which has never completed once has no working steps,
only unfalsified ones, and the count of round trips to green is the count of
distinct faults, not one.

AND THE SAME RULE ALREADY COVERED IT. The step sets GIT_CONFIG_COUNT,
GIT_CONFIG_KEY_0 and GIT_CONFIG_VALUE_0 in its env block, which is the same
instruction by a route the shell cannot touch. The inline `-c` is a second
implementation of one idea, and the one nobody looked at is the one that was
broken.
