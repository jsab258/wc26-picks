2026-09-07  THE SAME GLUED-STREAM BUG IS LATENT IN TWO MORE TOOLS, BOTH OF
            WHICH RUN ON JAFAR'S PC.
--------------------------------------------------------------------------
WHAT WAS FIXED TODAY was tools/runner/inbox.py, where git_call returned
stdout and stderr concatenated into one string and the caller then tested the
result against a 40-character sha. On a Windows checkout with core.autocrlf
on, git hash-object succeeds on stdout and prints a warning on stderr, the
two arrive glued, the match fails, and a successful command is reported as
"could not store". That held 254 of his messages on the PC.

THE SAME SHAPE IS STILL PRESENT IN:

  tools/pc-watcher.py:527   def git(...) returns (p.stdout + p.stderr).strip()
                            and six call sites parse a sha out of it:
                            lines 724, 763, 776, 908, 916, 1110. Four of
                            those read FETCH_HEAD, and pc-watcher HARD-RESETS
                            the checkout to what it reads.
  tools/runner/executor.py:636  its own git_call, same concatenation; line 723
                            parses `rev-parse --short HEAD`.

WHY IT IS LATENT AND NOT LIVE. rev-parse does not normally write to stderr,
so no failure has been observed from these. That is not a defence: the fixed
site did not normally write to stderr either, until the code ran on a checkout
with autocrlf on. Every one of these is one git configuration away from the
same silent stop. NOT FIXED TODAY because Jafar's standing rule for this batch
is no process changes and nothing outside the ordered items until the round
trip is proven.

WHAT THE FIX LOOKS LIKE, so it does not have to be rediscovered: split the
two streams at the helper rather than at the call sites, return three values,
and let the value come from stdout while the diagnosis comes from stderr.
inbox.py now carries a worked example and an accepting selftest case that
plants a real autocrlf warning and proves the push still lands.

2026-09-07  THE OUTBOX RETRIES A PERMANENTLY REFUSED MESSAGE FOR EVER, AND
            THAT IS WHAT THE "254 MESSAGES" ACTUALLY WERE.
--------------------------------------------------------------------------
MEASURED, NOT INFERRED. The pc-inbox branch carries exactly ONE message file
from Jafar, 2026-09-07T0550Z-79313218.md, which is the same file this
morning's push error named. Beside it sit 312 outbound records, of which 304
are refusals of a SINGLE file: production/outbox/2026-09-03-batch-landed-and-
the-wait.unprompted.md. One file, 304 refusals.

So the "254 messages sitting on the PC" that opened this morning were not 254
messages he typed. They were the outbound refusal backlog at that moment, and
it has since grown to 304 while the channel was being fixed. He read the
number off the bot window and reported it in good faith; the number was real
and it was counting something else.

THE BUG. `sweep_outbox` runs every 120 seconds, picks up the same unsent
Producer message, puts it through the register, is refused, and WRITES A NEW
REFUSAL RECORD. The refusal reasons are stable and self-inflicted: a deadline
now 26 hours in the past, a word cap 22 words over, and two links pointing
somewhere the 2026-09-06 ruling forbids. None of them can become true by
waiting, so the retry can never succeed and never stops. Unbounded growth in
a folder that rides the transport.

WHAT IT COSTS. Every one of those records is pushed, delivered, read back and
printed. The container's own report grows by a line per record for ever, and
`outbound_from_branch` runs one `git show` per record per run.

TWO FIXES, AND THEY ARE DIFFERENT. The message itself should be withdrawn or
repaired, since it is four days stale and can never pass. And the sweep needs
to stop writing a new record for a refusal it has already recorded for that
file with those reasons: a refusal that has not changed is not news.

NOT FIXED TODAY. His standing rule is no process changes until the clip
exists. Recorded with its count so the number is not rediscovered.
